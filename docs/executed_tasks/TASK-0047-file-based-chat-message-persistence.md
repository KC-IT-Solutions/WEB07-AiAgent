# TASK-0047 - File-based chat message persistence

Task ID: TASK-0047
Task slug: file-based-chat-message-persistence

## Goal

Persist chat message history as server-side files instead of storing messages in SQLite.

SQLite continues to own chat metadata.

This task implements the server-side message store, message retrieval API, and persistence of user/assistant messages produced by the existing inference endpoint.

Do NOT yet send previous conversation history to the model.

## Architecture

Follow:

    HTTP
      -> Application Service
      -> ChatMessageStore
      -> filesystem

Do not put filesystem operations directly in HTTP handlers.

Introduce a focused filesystem-backed abstraction such as:

    ChatMessageStore

The application/inference layer may depend on that abstraction, not directly on fs APIs.

Do not store chat messages in SQLite.

Do not add a database migration for messages.

## Storage location

Use a server-owned data directory outside the client/static assets.

Suggested structure:

    data/
      chat-history/
        user-1/
          chat-<chatId>.jsonl

The implementation may centralize/configure the root path appropriately.

Important:

- history files must never be served as static client files
- client input must never provide a filesystem path or filename
- construct paths only from trusted server-side numeric userId/chatId values
- protect against path traversal
- current fixed server-side UserId = 1 remains unchanged

The combination of userId and chatId must uniquely identify the history file.

Do not expose the physical filename/path through the API.

## File format

Use JSON Lines / JSONL.

One message per line.

Each persisted message must contain only the fields required now, for example:

    {
      "role": "user",
      "content": "Hello",
      "createdAt": 1787472000
    }

or:

    {
      "role": "assistant",
      "content": "Hello!",
      "createdAt": 1787472001
    }

Requirements:

- role is currently only "user" or "assistant"
- content must be a non-empty string
- createdAt is an integer Unix timestamp
- preserve file order as conversation order
- validate parsed stored data at runtime
- do not use `any`
- malformed stored JSON/message data must produce a controlled server error rather than silently returning corrupt history

Do not persist UI-only error messages or thinking indicators.

## Message store operations

Implement the minimum operations needed:

    listMessages(userId, chatId)
    appendMessage(userId, chatId, message)
    deleteHistory(userId, chatId)

Exact naming may follow repository conventions.

Requirements:

- create required history directories safely when first writing
- missing history file means an empty message list
- append messages without rewriting unrelated chat history
- preserve message ordering
- UTF-8
- deletion of a nonexistent history file must be safe/idempotent

## Chat ownership

Before reading or mutating message history, confirm that the chat belongs to the current server-side UserId.

Do not allow access to history merely because a numeric chat ID was supplied.

Reuse the existing ChatService ownership behavior rather than duplicating SQL in the file store.

## Retrieval API

Add:

    GET /api/chats/:id/messages

For an existing chat owned by UserId 1:

    {
      "messages": [
        {
          "role": "user",
          "content": "...",
          "createdAt": 123
        },
        {
          "role": "assistant",
          "content": "...",
          "createdAt": 124
        }
      ]
    }

Requirements:

- invalid chat ID -> existing safe validation/error style
- nonexistent/not-owned chat -> safe not-found behavior
- missing history file -> `{ "messages": [] }`
- do not return filesystem paths

Do not change the client in this task.

## Persist existing inference messages

Update the existing:

    POST /api/chats/:id/inference

flow so the server persists messages generated by that interaction.

Required order:

1. validate chat/message/model connection/model using existing behavior
2. append the accepted user message to the chat history
3. perform the existing model inference
4. on successful assistant response, append the assistant message
5. return the existing inference response shape

Do not change the response contract used by ChatView.

If inference fails after the user message was accepted:

- the user message may remain persisted
- do not persist a fake assistant/error message

Do not yet read old messages and send them to the model.

The model request must remain the existing single-message request for this task.

## Chat deletion

When an existing chat is successfully deleted:

- also delete that chat's history file

Requirements:

- deleting a chat with no history file still succeeds
- do not leave normal orphaned history files after chat deletion
- do not let a history-file cleanup failure silently delete arbitrary files
- stay within the configured history root

## Concurrency / safety

Keep this implementation simple but safe.

Do not introduce the global model inference queue in this task.

Ensure append operations for one history file cannot corrupt JSONL output during normal concurrent server requests.

A small per-file/per-chat write serialization mechanism is acceptable if needed.

Do not introduce a broad job/queue framework.

## Configuration and tests

Production/default storage must use the application data directory.

Automated tests must use isolated temporary directories.

Tests must never read/write real production chat-history files.

Do not use LM Studio.

Do not rely on machine-specific absolute paths.

## Tests

Add focused deterministic tests for at least:

- missing history file returns empty list
- user message append
- assistant message append
- append preserves ordering
- UTF-8 content
- malformed JSONL is rejected safely

- path is derived from trusted user/chat IDs
